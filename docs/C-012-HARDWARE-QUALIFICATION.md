# C-012 PRX126 hardware qualification matrix

**Status:** source-generated qualification plan, November 7, 2026.
**Baseline:** committed `AoTT-8311-v2r9` on
`potron-prx126-aott-v1`.

This milestone converts the existing 54-field capability registry into a
hardware-test plan. It does **not** change the ONU, approve a live mutation, or
claim that source validation proves a setting works on hardware.

The machine-readable matrix is
[`C-012-HARDWARE-QUALIFICATION-MATRIX.json`](C-012-HARDWARE-QUALIFICATION-MATRIX.json).
It is generated by
[`tools/build_c012_hardware_qualification.py`](../tools/build_c012_hardware_qualification.py)
from the canonical capability registry.

## Why a separate qualification matrix

The r9 configuration backend already provides a real schema, validation,
revision-aware preview, sequential environment writes, and durable readback.
The seven C-011 readback groups provide source contracts for all 54 fields.
Neither fact proves the complete hardware contract:

`read -> validate -> preview -> apply -> durable readback -> effective readback -> persistence -> recovery`

C-012 tracks those steps explicitly for every field and starts every hardware
test with a read-only baseline.

## Current lane counts

| Mutation lane | Fields | Meaning |
| --- | ---: | --- |
| `SAFE_LIVE_APPLY_CANDIDATE` | 4 | Preferred first mutation candidates after a fresh baseline, explicit authorization, known original value, and bounded revert |
| `RECOVERY_PATH_REQUIRED` | 25 | Do not mutate until an independent alternate management/recovery path is proven |
| `TEST_OLT_OR_SPARE_REQUIRED` | 25 | Do not use the production fiber connection as the first mutation target; use a spare/recoverable ONU and controlled OLT/service environment where applicable |

The four lower-risk candidates are `lang`, `hostname`, `timezone`, and
`ntp_servers`. Calling them candidates is **not preapproval** to change them.

Management addressing, host link/boot/pin controls, virtual SFP identity, and
the root password override require an alternate recovery path. PON identity,
registration, OMCI reporting/profile, and ISP/VLAN controls require a
spare/test-OLT lane because a syntactically valid value can still break
registration or subscriber service.

Secret handling is independent of the lane. `reg_id_hex`, `lpwd`, and
`root_pwhash` remain secret-classified and may never be copied into public
qualification artifacts.

## Proof stages

Every field begins with all hardware proof stages false:

1. Saved-value readback.
2. Read-only effective baseline.
3. Validated preview.
4. Native apply.
5. Durable readback.
6. Effective readback from the real consumer.
7. Service consequence.
8. Restart or reload behavior.
9. Reboot persistence.
10. Recovery or revert.
11. Negative and failure cases.

A field becomes `FULLY_QUALIFIED` only when all applicable stages have
independent evidence for the named hardware profile. Source references,
matching UCI values, O5.1, or a successful setter exit code are not enough.

## Immediate hardware work

The next hardware action is **read-only**, not a mutation: collect a bounded
baseline from the committed r9 runtime and record which of the existing
effective-state probes can produce genuine current evidence for each field.

Only after that baseline should the four lower-risk candidates be considered
for controlled mutation tests. Management, link/boot/pin, PON/OMCI, identity,
and VLAN fields stay behind their stronger gates.

## Safety and publication boundary

The generator reads source files only. It contains no SSH, HTTP, firmware,
boot-bank, environment-setter, or UBI mutation path. The generated matrix
contains field IDs, source evidence classifications, test gates, and proof
booleans only. It contains no live values, subscriber identifiers,
credentials, private addresses, or private recovery material.
